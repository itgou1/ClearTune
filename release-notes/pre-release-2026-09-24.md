## 发现

### P1 · 发布版本号与线上重复（发布准备阶段已修复）

[app/build.gradle.kts](../app/build.gradle.kts) 第 43–44 行仍为 `versionCode = 11`、`versionName = "1.4.0"`。通过 GitHub 只读查询确认，当前正式发布是 [v1.4.0](https://github.com/itgou1/ClearTune/releases/tag/v1.4.0)，发布时间为 2026-09-23 02:40:55 UTC；其版本号也是 11。

应用的更新判断只接受更大的 `versionCode`，发布工作流还要求标签与 `versionName` 一致。当前候选包可以通过 ADB 同签名覆盖安装，但这不能证明线上更新链路可用：沿用现有版本号不会被已有用户识别为新版本，现有 Git 标签也不能再次用于一次正常的新版本发布。

发布前需确定新版本名称，将 `versionCode` 增加到大于 11，保存本次经过验收的源码改动，重新构建并核对 APK/AAB、更新清单与新标签。此次没有擅自确定或修改版本号。

### P2 · 歌单分享数量可能与实际内容不一致（后续已修复）

代码审查发现：[ShareRepository.kt](../app/src/main/java/com/cleartune/app/share/ShareRepository.kt) 第 70 行起会在创建时重新读取服务器歌单，使用实时歌曲 ID 生成链接；但第 90、118 行仍保存打开面板时的 `target.songCount`，第 142 行又优先使用这份本地数量。

触发场景：分享面板打开时为 3 首，另一个客户端把歌单改为 2 首；点击生成时，服务器返回完整的 2 首歌，实际分享正确包含 2 首，但预览、发送文案和管理页仍可能写“3 首”。这是代码路径确认的边界缺陷，本次未做并发修改的设备复现。

建议以创建请求实际使用的歌单歌曲数量保存快照，并补充“面板打开后歌单发生变化”的回归用例。正常数量未变化的单曲、专辑、歌单分享已通过正式包实测。
